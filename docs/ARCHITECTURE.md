# Як влаштований бот

Цей документ — карта коду. Читай його перед тим, як відкривати файли.

## Шари

Код розкладено на шари. Кожен шар знає тільки про ті, що нижче:

```
          Telegram
             │  апдейти (повідомлення, натискання кнопок)
             ▼
┌─────────────────────────────┐
│ handlers/                   │  «Що користувач хоче?»
│   admin.py  student.py      │  Розбирає команду, перевіряє права,
│   common.py helpers.py      │  викликає сервіс, відповідає 👍 або помилкою
└──────────────┬──────────────┘
               ▼
┌─────────────────────────────┐
│ service.py   QueueService   │  «Виконати дію і показати результат»
│                             │  lock → дія → save → оновити повідомлення, тегнути
└──────┬───────────────┬──────┘
       ▼               ▼
┌─────────────┐  ┌─────────────┐
│ storage.py  │  │ render.py   │  Збереження (SQLite + кеш)
│             │  │             │  і вигляд (текст + кнопки)
└──────┬──────┘  └──────┬──────┘
       ▼                ▼
┌─────────────────────────────┐
│ queue_logic.py  parsing.py  │  Чиста логіка: що таке черга і що з нею
│                             │  можна робити. Не знає про Telegram і БД.
└─────────────────────────────┘
```

Чому так: найважливіша частина, правила черги, лежить у `queue_logic.py` і не залежить ні від чого. Її можна тестувати звичайними функціями за мілісекунди (`tests/test_queue_logic.py`). Якщо колись захочеться перейти на іншу бібліотеку замість aiogram або на іншу базу, логіка черги не зміниться.

## Файли

| Файл | Що всередині |
|---|---|
| `bot/queue_logic.py` | `Slot`, `Queue`, статуси, усі дії: `join`, `leave`, `start`, `finish`, `skip`, `later`, `here`, `add`, `remove`, `close` |
| `bot/parsing.py` | Розбір часу (`10:25`) і аргументів `/new` → список часу слотів |
| `bot/storage.py` | SQLite (таблиці `queues`, `slots`, `users`) + словник активних черг у пам'яті |
| `bot/render.py` | Текст закріпленого повідомлення, кнопки, теги `tg://user?id=` |
| `bot/service.py` | `QueueService.apply()`, через який проходить кожна дія; фонове оновлення повідомлення |
| `bot/permissions.py` | Чи людина адмін групи (з кешем) |
| `bot/handlers/` | Обробники aiogram: команди, кнопки, «Закінчив» |
| `bot/config.py` | Читання `BOT_TOKEN` з `.env` |
| `bot/__main__.py` | Запуск: створює Bot, Storage, Service, Dispatcher і стартує polling |

**Рекомендований порядок читання:** `queue_logic.py` → `tests/test_queue_logic.py` → `render.py` → `service.py` → `handlers/student.py` → решта.

## Головна ідея логіки черги

Кожен слот має статус:

```
EMPTY ──join──► WAITING ──(черга дійшла)──► CURRENT ──finish──► DONE
                   ▲                           │
                   └────────── here ◄── SKIPPED ◄──skip──┘
```

Є одне правило, з якого випливає все інше: **поточним стає перший за часом слот зі статусом WAITING.** Це робить `_advance()`, і вона викликається після кожної дії.

З цього правила випливає кілька наслідків:
- порожні слоти пропускаються самі собою;
- пропущений студент після `/here` стає наступним, бо його слот раніший за інших, хто чекає;
- `later` просто міняє людей місцями між двома слотами, а статуси лишаються на своїх слотах.

Щоб не можна було перестрибнути чергу, після старту не можна записатися в слот, час якого вже минув (`_cursor()`).

## Шлях одного натискання «✅ Я закінчив»

1. Telegram надсилає апдейт `callback_query` з даними `q:done:7` (7 — id черги).
2. `handlers/student.py: on_button` розбирає дані і визначає чергу за чатом і топіком.
3. `_finish` перевіряє права. Якщо натиснув сам поточний студент, запиту до Telegram немає. Якщо хтось інший, бот питає, чи це адмін (результат кешується на 5 хв).
4. `service.apply(key, lambda q: q.finish(...))`:
   - бере `asyncio.Lock` черги, щоб два одночасні натискання не переплутались;
   - виконує `finish` у пам'яті;
   - зберігає в SQLite;
   - питає чергу `pop_turn_change()`, тобто чи змінився поточний.
5. Обробник одразу відповідає спливаючим повідомленням «✅ Записав…». Для студента на цьому все: дія виконана.
6. **У фоні** сервіс:
   - редагує закріплене повідомлення, не частіше разу на секунду, щоб не впертися в ліміти Telegram;
   - надсилає «▶️ @наступний, твоя черга! ⏳ @той що за ним, готуйся».

## Чому бот швидкий

- **Стан у пам'яті.** Щоб дізнатися, хто зараз здає, не треба читати з диска: усі активні черги лежать у словнику. SQLite потрібен тільки для збереження на випадок перезапуску.
- **SQLite у режимі WAL.** Запис займає частки мілісекунди.
- **Відповідь раніше за оновлення.** Редагування повідомлення і теги йдуть фоновими задачами, тож користувач не чекає на мережу.
- **Зливання оновлень.** Якщо за секунду записалося 10 людей, повідомлення редагується 1–2 рази, а не 10. Це також захищає від `429 Too Many Requests`.
- **Кеш адмінів.** Запит `getChatAdministrators` іде раз на 5 хвилин, і тільки для адмінських дій.
- **Мінімум апдейтів.** Бот підписаний тільки на `message` і `callback_query`.

## Що бот бачить у групі

Privacy mode (налаштування в @BotFather) **лишається увімкненим**. Тоді бот отримує тільки:
- команди (`/join`, `/done@queue_bot`, …);
- відповіді на свої повідомлення (звідси «Закінчив» у відповідь);
- натискання своїх кнопок.

Звичайну переписку групи бот не читає.

## Тести

```powershell
uv run pytest
```

- `test_queue_logic.py`: правила черги.
- `test_parsing.py`: розбір `/new` і часу.
- `test_storage.py`: збереження та відновлення після перезапуску.
- `test_render.py`: вигляд повідомлення і кнопок.
- `test_bot_flow.py`: **наскрізний** тест. Справжній aiogram Dispatcher і обробники, але замість Telegram стоїть `FakeSession`, яка записує, що бот надіслав. Перевіряє повну пару: створення, запис, старт, «Закінчив», закриття.
